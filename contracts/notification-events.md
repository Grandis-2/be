# 알림 이벤트 계약 (preorder · order → member)

회원 화면의 알림(종 아이콘)을 만드는 메시지다. 알림이 생길 일을 아는 서비스(preorder · order)가 보내고 member 가 받아 `notifications` 표에 받는 회원마다 한 행씩 저장한다. 화면은 member 의 조회 API 로 읽는다. 실제 발송(문자 · 메일 · 앱 푸시)은 없다 — 저장과 지표가 곧 Mock 발송이다. 문서와 어긋나는 쪽이 고친다.

보내는 쪽은 업무 상태를 바꾸는 트랜잭션에서 자기 아웃박스에 `NOTIFICATION_REQUESTED` 를 적고, 커밋 뒤 SQS 로 보낸다. 상태가 실제로 바뀐 때만 적는다 — 같은 결과를 다시 받아 상태가 그대로면 적지 않는다(아웃박스 행마다 eventId 가 새로 나서 member 가 막을 수 없다). 알림은 업무를 되돌리지 않는다 — member 가 내려가 있어도 메시지는 큐에서 기다린다.

## 전달

| 이벤트 | 큐 | 받는 쪽 |
| --- | --- | --- |
| `NOTIFICATION_REQUESTED` | `notification` | member — 받는 회원마다 알림 한 행을 저장한다 |

- **최소 한 번.** 커밋 직후 한 번 보내고, 못 보냈으면 릴레이가 다시 보낸다. member 는 `(eventId, 받는 회원)` 으로 중복을 막는다 — 같은 메시지를 두 번 받아도 회원마다 알림은 한 건이다.
- **순서 보장 없음.** 알림끼리 순서에 기대지 않는다. 화면은 `occurredAt` 순으로 보인다.
- **메시지 하나 = 같은 알림을 받는 회원 1~1,000명.** 같은 문구를 여러 회원에게 보낼 때(오픈 알림 신청자) 1,000명씩 묶어 한 메시지로 보낸다 — 신청자 1만 명이면 아웃박스 행 · 메시지 10개다. 한 명이면 목록에 한 명이다. 1,000명이면 본문이 약 40KB 라 SQS 한도(256KB) 안이다.
- **이벤트 종류는 하나다.** 알림 종류는 `payload.kind` 로 가르고, member 는 종류를 몰라도 저장한다. 그래서 새 알림을 추가할 때 member 를 먼저 배포하지 않아도 된다.
- **메시지 속성.** `eventType` · `eventId`(문자열). 다른 이벤트와 같다.

## 봉투

다른 이벤트와 같은 `EventEnvelope` 다.

```json
{
  "eventId": "6f1c2a7e-0d3b-4c8f-9a51-2b7d8e4f0c19",
  "eventType": "NOTIFICATION_REQUESTED",
  "aggregateType": "PREORDER",
  "aggregateId": "0199a3f2-8a10-7b21-9c32-4d5e6f708192",
  "occurredAt": "2026-10-15T03:00:00.123456Z",
  "payload": {
    "recipientIds": ["0199a3f0-0000-7000-8000-000000000002"],
    "kind": "PREORDER_REGISTERED",
    "title": "사전예약 등록 완료",
    "body": "사전예약 등록이 완료됐어요. 24시간 안에 결제해 주세요.",
    "target": { "type": "PREORDER", "id": "3c0f6a52-6d1b-4f7e-9b2a-0e5d8c1f4a77" }
  }
}
```

| 칸 | 뜻 |
| --- | --- |
| `aggregateType` · `aggregateId` | 알림이 생긴 원인(예약 · 회차 · 응모 · 주문). member 는 추적용으로만 저장한다. `aggregateType` 은 30자 이하 |
| `payload.recipientIds` | 받는 회원 id 목록(UUID 문자열) 1~1,000개, 겹치지 않게. 비었거나 1,000개를 넘거나 겹치면 거절한다 |
| `payload.kind` | 알림 종류(아래 표). 화면의 아이콘 · 분류용이다. member 는 값을 검사하지 않는다 |
| `payload.title` | 제목. 1~100자 |
| `payload.body` | 본문. 1~500자 |
| `payload.target` | 누르면 갈 곳. `type` 과 `id`(문자열)만 싣고, 주소는 프론트가 만든다 — 프론트가 주소를 바꿔도 저장된 알림이 깨지지 않게 |

**왜 값을 싣는가.** 다른 이벤트의 받는 쪽은 aggregateId 로 자기 원장을 다시 읽지만, member 에는 예약 · 응모를 읽는 길이 없다. 그래서 화면에 보일 값을 보내는 쪽이 완성해 payload 에 담는다. 문구도 보내는 쪽이 정한다.

**모르는 칸은 무시한다.** 보내는 쪽이 칸을 더해도 먼저 배포된 member 가 깨지지 않는다. 칸을 빼거나 뜻을 바꿀 때만 양쪽을 맞춘다.

## 알림 종류

| `kind` | 보내는 쪽 | 언제 | 받는 사람 | `aggregateType` | `target` |
| --- | --- | --- | --- | --- | --- |
| `PREORDER_REGISTERED` | preorder | 예약이 외부 등록을 마쳐 `REGISTERED` 가 될 때 | 예약한 회원 | `PREORDER`(예약 내부 id) | `PREORDER` · 예약 공개 토큰(`preorderToken`) |
| `PREORDER_CANCELED` | preorder | 예약 취소가 끝나 `CANCELING → CANCELED` 가 될 때(아래 "취소 알림") | 예약한 회원 | `PREORDER`(예약 내부 id) | `PREORDER` · 예약 공개 토큰(`preorderToken`) |
| `DRAW_WON` | order | 추첨 결과를 반영할 때 — 당첨 응모 | 응모한 회원 | `DRAW_ENTRY`(응모 id) | `DRAW` · 회차 id |
| `PREORDER_OPENED` | preorder | 회차가 열릴 때(아래 "오픈 알림") | 그 상품에 오픈 알림을 신청한 회원 | `PREORDER_CAMPAIGN`(상품 id) | `PRODUCT` · 상품 id |
| `PAYMENT_UNCONFIRMED` | order | 장바구니 · 바로 구매 주문을 결제 결과를 끝내 몰라 취소할 때(만든 뒤 20분, `AUTHORIZING → CANCELED`) | 주문한 회원 | `ORDER`(주문 id) | `ORDER` · 주문 id |
| `PREORDER_PAYMENT_FAILED` | order | 사전예약 주문의 결제가 나중에 실패로 확정돼 결제 대기로 돌아갈 때(결과 이벤트의 거절 · 만료). 승인 응답으로 바로 받은 거절은 화면이 이미 보여 보내지 않는다 | 주문한 회원 | `ORDER`(주문 id) | `PREORDER` · 예약 공개 토큰(없으면 `ORDER` · 주문 id) |

문구는 오픈 알림의 상품명과 취소 알림의 본문(취소 까닭 · 결제 여부)을 빼면 고정이다. 드로우는 당첨자에게만 보낸다 — 낙첨은 드로우 상세(내 응모 결과)에서 본다. 결과 반영 트랜잭션이 회차를 잠근 채 도는데, 낙첨까지 보내면 그 안의 INSERT 가 응모 수만큼 늘기 때문이다(당첨 인원만큼이면 당첨 주문을 만드는 수와 같다).

| `kind` | `title` | `body` |
| --- | --- | --- |
| `PREORDER_REGISTERED` | 사전예약 등록 완료 | 사전예약 등록이 완료됐어요. 24시간 안에 결제해 주세요. |
| `PREORDER_CANCELED` | 사전예약 취소 | 사용자 취소: 사전예약 취소가 완료됐어요.<br>결제 기한 만료: 결제 기한이 지나 사전예약이 취소됐어요.<br>관리자 취소 · 회차 판매 중지: 사전예약이 취소됐어요.<br>결제된 예약이면 뒤에 ` 결제하신 금액은 환불됐어요.` 를 붙인다 |
| `DRAW_WON` | 럭키 드로우 당첨 | 축하해요! 럭키 드로우에 당첨됐어요. |
| `PREORDER_OPENED` | 사전예약 오픈 | 알림 신청하신 `{상품명}` 사전예약이 시작됐어요. |
| `PAYMENT_UNCONFIRMED` | 결제 확인 실패 | 결제를 확인하지 못해 주문이 취소됐어요. 결제된 금액이 있으면 자동으로 환불돼요. |
| `PREORDER_PAYMENT_FAILED` | 결제 실패 | 결제가 완료되지 않았어요. 내 예약에서 결제 상태를 확인해 주세요. |

**`target.type` 과 프론트 화면.**

| `type` | `id` | 화면 | 상세 API |
| --- | --- | --- | --- |
| `PRODUCT` | 상품 id | 사전예약 상품 상세 | `GET /api/v1/products/{productId}` |
| `PREORDER` | 예약 공개 토큰 | 내 예약 상세 | `GET /api/v1/preorders/{preorderId}` (공개 토큰) |
| `DRAW` | 회차 id | 드로우 상세 · 내 응모 결과 | `GET /api/v1/draws/{drawId}` · `GET /api/v1/draws/{drawId}/entries/me` |
| `ORDER` | 주문 id | 주문 상세 | `GET /api/v1/orders/{orderId}` |

모르는 `type` 이 오면 프론트는 이동하지 않고 알림만 보인다(종류가 늘 수 있다).

## 취소 알림

취소는 어느 주체로 시작하든(사용자 · 관리자 · 만료 · 회차 판매 중지, 외부 등록 전 취소 포함) 주문 정리(`PREORDER_ORDER_SETTLED` 의 `NO_ORDER` · `CANCELED`) → 외부 취소 작업 성공으로만 끝난다. preorder 는 그 성공을 반영해 예약이 실제로 `CANCELED` 가 된 트랜잭션에서 한 번 적는다 — 성공 결과를 다시 받아도 이미 `CANCELED` 라 적지 않는다. 취소가 거절돼(`REJECTED`) `REGISTERED` · `RESERVED` 로 돌아가면 보내지 않는다. 취소 요청 순간에는 보내지 않는다(거절될 수 있다).

- **까닭.** 예약 행에 취소 까닭 칸이 없어, 이번 취소 시도의 `CANCELING` 진입 이력 주체로 정한다 — 사용자(`USER`) · 만료(`SYSTEM`) · 관리자(`ADMIN`). 회차 판매 중지도 주체가 `ADMIN` 이라 관리자 취소와 같은 문구다. 이력을 찾지 못하면 "사전예약이 취소됐어요." 로 보낸다.
- **결제 여부.** 예약의 결제 확인 시각(`reserved_at`)이 있으면 결제된 예약이다. 결제 확인 이벤트가 취소 완료보다 늦게 오면 환불 문장이 빠진다(드물고, 문구만 덜 자세하다).
- **환불은 끝나 있다.** 결제된 주문은 취소 중(`CANCELING`)으로 바뀌고 환불 완료(`REFUND_COMPLETED`)로만 `CANCELED` 가 되며, order 는 그 뒤에야 `CANCELED` 결과를 보낸다. 예약은 그 결과 → 외부 취소 성공 뒤에 `CANCELED` 가 되므로 알림 시점엔 환불이 끝나 있다 — 그래서 "환불돼요" 가 아니라 "환불됐어요" 다. 환불이 확정 실패하면 주문이 취소 중에 남아 예약도 취소 중에 머물고 알림은 없다. 만료 취소는 결제된 주문을 환불하지 않고 거절하므로 만료 문구에 환불 문장이 붙는 일은 없다. 환불이 확정 실패한 주문을 사람이 해소해 취소로 닫는 경우는, 수동 환불을 확인한 뒤 닫는다는 운영 전제로 같은 문구를 쓴다.

## 오픈 알림

회원이 오픈 전 사전예약 상품에 "오픈 알림 신청"을 해 두면, 회차가 열릴 때 신청자에게만 보낸다. 신청은 preorder 가 갖는다(`preorder_open_alerts`, 신청 · 해제 `PUT` · `DELETE /api/v1/preorders/products/{productId}/open-alert`, 내 목록 `GET /api/v1/preorders/open-alerts`). 비공개 상품은 404, 판매 중지는 `PRODUCT_PAUSED`(409), 이미 열렸으면 `PRODUCT_ALREADY_OPEN`(409). 오픈은 누가 누르는 동작이 아니라 시각이 지나는 것이라 preorder 가 주기적으로(기본 30초) 회차를 찾는다.

- **대상.** `opens_at ≤ 지금` 이고 `open_notified_at IS NULL` 이며 연 지 1시간이 안 됐고 아직 마감 전인 회차. 처음 배포할 때 오래전에 열린 회차의 알림이 몰려 나가지 않게, 장애가 길면 늦은 알림을 포기한다. 이미 마감(조기 마감 · 회차 취소)된 회차에는 "시작됐어요" 를 보내지 않는다.
- **두 단계로 보낸다.** 회차 행은 접수가 순번을 받으려 잠그는 행이라, 오픈 순간 그 행을 오래 잡으면 접수가 신청자 수만큼 기다린다.
  - 표시: 짧은 트랜잭션 하나에서 조건부 UPDATE(`open_notified_at IS NULL` 과 위 조건 · 공개 · 판매 중지 아님)로 채우고, 영향 행이 1 이면 발송 진행 행(`preorder_open_alert_dispatches`)을 넣고 커밋한다. preorder 가 여러 대여도 표시는 한 번이다.
  - 묶음: 묶음마다 따로인 짧은 트랜잭션에서 진행 행을 잠그고(회차 행이 아니다), 커서 다음 신청자 1,000명을 `customer_id` 순으로 읽어 아웃박스에 한 행 적고 커서를 옮긴다. 1,000명이 안 차면 발송을 끝낸다(`completed_at`). 아웃박스 행과 커서가 같이 커밋되므로 묶음은 한 번씩이고, 여러 대가 같은 회차를 이어도 진행 행에서 줄 선다.
- **이어 보내기.** 주기 작업은 끝나지 않은 진행 행(앞 주기에 죽은 것 포함)을 커서부터 이어 보낸다. 묶음 하나가 실패하면 그 묶음만 롤백되고(아웃박스 행 · 커서 함께) 다음 주기에 다시 한다. 묶음마다 진행 행을 잠근 뒤 그 시각으로 회차를 다시 보고, 마감됐거나 · 연 지 1시간이 지났거나 · 비공개 · 판매 중지면 남은 신청자에게 보내지 않고 발송을 끝낸다(`completed_at`). 회차마다 WARN 로그 한 번과 지표 `preorder.open_alert.abandoned{reason=CLOSED|WINDOW_PASSED|HIDDEN|PAUSED}` 를 남긴다. 표시 뒤라 다시 공개 · 판매돼도 보내지 않는다.
- **오픈 경계의 신청.** 신청은 회차 행을 공유 잠금한 뒤, 잠금을 얻은 시각으로 "오픈 전이고 아직 표시 전인가" 를 본다. 표시의 UPDATE 는 그 잠금이 풀리길 기다리므로, 표시 전에 잡은 신청은 표시보다 먼저 커밋돼 표시 뒤에 시작하는 묶음이 읽는다. 표시 뒤의 신청은 `PRODUCT_ALREADY_OPEN`(409)으로 막혀 빠지는 신청자가 없다.
- **상품명 · 판매 상태는 preorder 의 사본으로 본다.** catalog 가 상품을 등록 · 수정할 때 이벤트로 상품명 · 판매 상태 · 공개 여부를 변경 번호와 함께 보내고, preorder 가 회차 행에 적어 둔다(`contracts/catalog-events.md`). 주기 작업에는 회원 토큰이 없어 catalog API 를 부를 수 없고, catalog 표는 직접 읽지 않는다. 상품 수정은 오픈 3분 전부터 막혀 오픈 순간의 사본은 최신이다.
- **건너뛰기.** 비공개 · 판매 중지면 보내지 않고 표시도 채우지 않는다 — 1시간 안에 다시 공개 · 판매되면 그때 보낸다. 표시할 회차를 찾는 조회가 이 둘을 미리 걸러 한 주기 상한을 차지하지 않는다. 창 안의 이런 회차 수만큼 주기마다 지표 `preorder.open_alert.skipped{reason=HIDDEN|PAUSED}` 가 오르고, 보내지 못한 채 1시간 창이 지나면 인스턴스마다 한 번 INFO 로그에 이유를 남긴다. 판매 상태 사본을 아직 받지 못한 회차(null)는 막지 않는다.
- **상품명이 없으면.** 사본을 받기 전 회차는 본문을 "알림 신청하신 사전예약이 시작됐어요." 로 보내고 경고 로그를 남긴다.
- **표시는 회차당 한 번.** 표시는 오픈 뒤에만 채우고 오픈 뒤에는 일정을 바꿀 수 없어, 표시를 비우고 다시 보내는 길은 없다. 진행 행이 이미 있으면 버그로 보고 표시까지 롤백한다(진행 중인 커서를 덮지 않는다).
- **신청자가 없으면** 표시만 채우고 메시지는 없다(진행 행은 첫 묶음에서 끝난다).

## 조회 API

member 가 내놓는다. 회원 전용(USER 토큰) — 토큰 없으면 401, 관리자 토큰은 403. 남의 알림은 보이지도 바뀌지도 않는다. 응답은 다른 API 와 같은 `ApiResponse` 봉투(`data`)에 싼다 — 실시간 연결의 이벤트만 봉투 없이 온다(아래 "실시간 연결").

| 요청 | 하는 일 | 성공 응답 |
| --- | --- | --- |
| `GET /api/v1/notifications/stream` | 안 읽은 수 실시간 연결(SSE). 연결 뒤 한 주기(2초) 안에, 그리고 내 알림이 새로 저장될 때마다 수를 보낸다 | 200 `text/event-stream` |
| `GET /api/v1/notifications?cursor=&size=` | 내 알림, 최신순(`createdAt` · `notificationId` 내림차순) 커서 페이징. `size` 1~50(기본 20). 깨진 커서 · 범위 밖 size 는 400 | 200 `{ "items": [...], "nextCursor": "..." }` — `nextCursor` 가 null 이면 마지막 쪽. 총계는 없다 |
| `GET /api/v1/notifications/unread-count` | 안 읽은 수. 실시간 연결이 끊긴 동안 헤더 배지가 주기적으로 부른다 — 인덱스만 읽는다 | 200 `{ "count": 3 }` |
| `PATCH /api/v1/notifications/{notificationId}/read` | 하나 읽음. 이미 읽었으면 그대로(처음 읽은 시각 유지). 남의 알림 · 없는 id 는 같은 404 | 204 본문 없음 |
| `POST /api/v1/notifications/read-all` | 내 안 읽은 알림 모두 읽음 | 204 본문 없음 |

항목 하나:

```json
{
  "notificationId": "0199a3f3-1c2d-7e4f-8a5b-6c7d8e9f0a1b",
  "kind": "DRAW_WON",
  "title": "럭키 드로우 당첨",
  "message": "축하해요! 럭키 드로우에 당첨됐어요.",
  "target": { "type": "DRAW", "id": "0199a3f2-8a10-7b21-9c32-4d5e6f708192" },
  "read": false,
  "createdAt": "2026-10-15T03:00:00.123456Z"
}
```

`message` 는 payload 의 `body`, `createdAt` 은 봉투의 `occurredAt`(UTC)이다. 주소 대신 `target` 을 주므로 이동할 화면은 위 "`target.type` 과 프론트 화면" 표로 프론트가 정한다.

### 실시간 연결

헤더 배지(안 읽은 수)를 새 알림 뒤 2초 안팎에 바꾼다. 인증은 다른 API 와 같은 `Authorization: Bearer` 헤더라, 브라우저 기본 `EventSource`(헤더를 못 싣는다) 대신 fetch 기반 SSE 클라이언트로 연결한다.

- **이벤트.** `event: unread` · `data: {"count": 3}` — 봉투 없이 수만 싣는다. 연결 뒤 한 주기(2초) 안에 한 번(지금 수), 그 뒤 내 알림이 저장될 때마다 온다. 연결은 DB 를 읽지 않고 태스크가 주기마다 새 연결을 묶어 센다 — 배포 뒤 수천 연결이 한꺼번에 다시 붙어도 DB 풀이 다른 API 를 막지 않게. 같은 수가 거듭 올 수 있어 화면은 받은 값으로 덮어쓴다. 읽음 표시(하나 · 모두)는 이 연결로 오지 않는다 — 읽은 화면이 지금처럼 스스로 다시 센다.
- **주기 신호.** 25초마다 SSE 주석 한 줄(`:`)이 온다. 화면은 무시한다. CloudFront(원본 읽기 60초) · ALB(유휴 65초)가 조용한 연결을 끊지 않게 하는 것이다.
- **수명 · 다시 연결.** 액세스 토큰 만료와 30분 중 이른 때, 그리고 배포로 태스크가 내려갈 때 서버가 닫는다. 화면은 (토큰이 만료됐으면 재발급한 뒤) 0~5초 사이 무작위로 기다렸다 다시 연결하고, 연달아 실패하면 간격을 늘린다 — 배포 때 모든 화면이 같은 순간에 붙지 않게. 첫 이벤트가 끊긴 동안의 수를 맞춘다. 로그아웃하면 화면이 연결을 닫는다(서버는 연결한 뒤 폐기를 다시 보지 않는다).
- **오류.** 연결 전 오류는 `Accept: text/event-stream` 이어도 다른 API 와 같은 JSON 봉투다. 401 은 토큰을 재발급해 다시 연결한다. 503 `DEPENDENCY_UNAVAILABLE` 은 이 태스크의 연결이 가득 찼거나(태스크당 5,000) 내려가는 중이라는 뜻이다 — 주기 조회로 돌아가고 잠시 뒤 다시 연결해 본다.
- **연결 수.** 회원 하나가 한 태스크에 5개(탭 · 기기)까지 연다. 여섯 번째를 열면 그 태스크의 가장 오래된 연결이 닫힌다.
- **주기 조회는 끊긴 동안에만.** 연결이 없을 때만 지금처럼 60초마다 `unread-count` 를 부르고, 연결된 동안에는 안전망으로 5분마다만 부른다(아래 "실시간으로 가지 않는 알림").
- **왜 DB 를 읽는가.** 알림을 저장한 태스크와 그 회원의 연결을 가진 태스크가 다를 수 있다(1~3대 + 배포 중 1대). 서버 사이 메시지(Valkey pub/sub) 대신 연결을 가진 태스크마다 2초마다 새 알림을 기본키(v7 id 라 시각순) 범위로 읽어 자기 연결의 회원만 센다 — 연결이 없으면 읽지 않고, 놓친 메시지를 되살릴 장치가 필요 없다.
- **실시간으로 가지 않는 알림.** 새 알림은 앞 주기를 시작한 시각보다 10초 앞부터 다시 읽어 늦게 커밋된 행을 잡는다. id 를 만든 뒤 커밋까지 10초를 넘긴 알림, 시계가 10초 넘게 뒤처진 태스크가 저장한 알림은 실시간으로 가지 않는다 — 5분 안전망 조회 · 다음 연결이 잡는다.

## 실패 처리

member 는 실패를 둘로 가른다. 섞으면 DB 순단 한 번에 멀쩡한 알림이 DLQ 로 가거나, 고칠 수 없는 메시지가 재수신 한도까지 헛돈다.

| 실패 | 예 | member 의 처리 | 결과 |
| --- | --- | --- | --- |
| **계약 위반** — 다시 받아도 같다 | JSON 이 아님 · 다른 eventType · 발생 시각이 1000-01-01 ~ 9999-12-31 밖 · 빈 제목 · 길이 초과 · recipientIds 가 없거나 비었거나 1,000개 초과 · 겹침 · UUID 아님 | 한 번 받고 `notification-dlq` 에 바로 넣고 원본을 지운다. 속성 `deadLetterReason` 에 이유(`UNREADABLE` · `NOT_NOTIFICATION` · `INVALID_ENVELOPE` · `INVALID_PAYLOAD`)를 붙인다. DLQ 에 넣지 못하면 원본을 남겨 다시 받는다 | 지표 `member.notifications.rejected{reason}` · ERROR 로그. 보내는 쪽 버그다 |
| **일시 오류** — 다시 하면 될 수 있다 | DB 연결 끊김 · 시간 초과 | 지우지 않고 지수 백오프(지터)로 늦춰 다시 받는다 | 재수신 한도(5회)를 넘기면 재드라이브 정책이 DLQ 로 옮긴다(이유 속성 없음) |
| **중복** | 릴레이 재전송 · 소비자 두 대가 같은 메시지 | 저장 전에 그 eventId 로 이미 넣은 회원을 읽어 건너뛰고 나머지만 넣는다(유니크 키 `(event_id, customer_id)`). 읽은 뒤 다른 소비자가 먼저 넣었으면 유니크 키에 걸려 일시 오류로 다시 받고, 그때 모두 건너뛴다 | 지표 `member.notifications{outcome=duplicate}` — 건너뛴 회원 수 |

**백오프와 DLQ 까지의 시간.** 운영 설정(인프라 `application/member/application.yml`)은 첫 대기 30초 · 상한 5분이다. 다섯 번 실패해 DLQ 로 가기까지 약 6~12분이다(지터 때문에 폭이 있다) — DB 가 그 안에 돌아오면 알림은 늦을 뿐 DLQ 로 가지 않는다. 코드 기본값과 로컬 예시도 30초다 — 5초면 약 1~3분이라 짧은 DB 순단에도 DLQ 가 찬다.

**DLQ 를 비우는 법.**
- `deadLetterReason` 이 있는 메시지(계약 위반): 보내는 쪽을 고친다. 메시지 자체는 다시 보내도 또 거절되므로 내용을 확인하고 버린다. 놓친 알림이 꼭 필요하면 보내는 쪽에서 다시 발행한다.
- 이유 속성이 없는 메시지(일시 오류로 한도를 넘김): 원인(DB 등)이 풀린 뒤 SQS 콘솔의 DLQ redrive 로 `notification` 에 되돌린다. `(eventId, 받는 회원)` 으로 중복을 막으므로 이미 저장된 것이 섞여도 안전하다.
- 같은 메시지가 DLQ 에 두 번 있을 수 있다 — DLQ 에 넣은 뒤 원본 지우기가 실패하면 다시 받아 한 번 더 넣는다. 거절 지표도 그만큼 오른다.
- 보존 기간: 본 큐 4일, DLQ 14일. 재드라이브로 옮겨진 메시지의 만료는 처음 큐에 들어간 시각 기준이다.

| 이름 | 뜻 | 볼 것 |
| --- | --- | --- |
| `member.notifications{outcome, kind}` | 저장 · 중복 행 수(받는 회원 수로 센다). `kind` 는 아는 종류만 그대로, 모르는 종류는 `OTHER` | 종류별 발송량. `OTHER` 가 보이면 member 의 종류 목록을 늘린다 |
| `member.notifications.rejected{reason}` | 계약 위반으로 DLQ 에 넣은 건수 | 0 이 아니면 보내는 쪽 버그 |
| `member.notifications.lag` | 보낸 쪽 발생 시각부터 저장까지. 새로 넣은 행이 있는 메시지마다 한 번 | 늘면 큐가 밀린 것(소비기 멈춤 · 처리량 부족) |
| `preorder.open_alert.skipped{reason}` | 오픈 알림 창 안에서 비공개(`HIDDEN`) · 판매 중지(`PAUSED`)로 건너뛴 회차 수. 주기마다 센다 | 오른 채 1시간 넘게 이어지면 그 회차는 알림 없이 창이 끝난다(INFO 로그에 이유) |
| `preorder.open_alert.abandoned{reason}` | 이어 보내던 발송을 남은 신청자에게 보내지 않고 끝낸 회차 수. 마감(`CLOSED`) · 1시간 창 경과(`WINDOW_PASSED`) · 비공개(`HIDDEN`) · 판매 중지(`PAUSED`) | 0 이 아니면 발송이 오래 막혔거나 발송 중에 상품이 내려갔다(WARN 로그에 상품 id) |
| `preorder.open_alert.pending` · `preorder.open_alert.pending.oldest.age` | 끝나지 않은 발송 수와 가장 오래된 것의 나이(초). 상태 지표 주기(기본 30초)로 DB 에서 센다. 인스턴스마다 같은 값이다 | 발송은 표시한 주기 안에 끝난다. 나이가 몇 분을 넘게 자라면 묶음이 계속 실패하는 것이다(ERROR 로그) |
| `member.notification.streams` | 이 태스크에 열린 실시간 연결 수 | 태스크당 상한(5,000)에 가까우면 새 연결이 503 이다 — 태스크를 늘린다 |
| `member.notification.stream.pushes{outcome}` | 안 읽은 수를 쓴 결과(첫 수 포함). `sent` 썼다 · `failed` 쓰다 실패해 닫았다 · `skipped` 앞 쓰기가 끝나지 않아 들고 있던 수가 더 새 수에 밀렸다 | `failed` 가 `sent` 에 비해 크면 연결이 중간에서 끊기고 있다(주기 신호 · 프록시 제한). `skipped` 가 꾸준하면 느린 클라이언트가 있다 — 쓰기는 연결마다 따로라 다른 연결은 늦지 않는다 |
| `member.notification.stream.tail` | 연결을 가진 태스크의 한 주기(새 알림 읽기 · 세기) 시간. 연결이 없으면 읽지도 재지도 않는다 | 2초에 가까워지면 배지가 늦다 — 몰린 알림이나 DB 지연 |
| CloudWatch `notification` 메시지 나이 · `notification-dlq` 적재 | 인프라가 큐마다 자동으로 건다 | Slack 경보 |

## 처리량 · 지연

알림이 화면에 닿기까지 세 구간을 지난다. 아래 수치는 추정이다(실측 아님).

- **보내는 쪽 발행.** 커밋 직후 발행은 서비스당 동시 32건까지다. 넘친 행은 기다리지 않고 릴레이에 맡겨지고, 릴레이는 1분 지난 미발행 행을 10초마다 100건씩 보낸다. 예약 등록 완료처럼 한 건씩 생기면 곧바로 나간다. 한 트랜잭션에 32건 넘게 몰리면(당첨 인원이 32명을 넘는 드로우) 32건 뒤는 1분 + 100건당 10초가 걸린다.
- **member 저장.** 메시지 하나를 이미 넣은 회원 읽기(SELECT) 한 번 + 여러 행 INSERT 한 번으로 넣는다 — 회원마다 INSERT 하면 NCP 왕복(약 35ms)이 회원 수만큼 쌓여 1,000명에 35초다. 트랜잭션으로 묶지 않는다(INSERT 한 문장이라 원자적이고, 읽기와 쓰기 사이의 경합은 유니크 키가 막는다). 왕복 2번이라 메시지당 100ms 안팎이고 받는 회원 수에 거의 매이지 않는다(1,000명이면 본문 · 행 쓰기로 수백 ms 더 든다고 본다) — 추정이다. 소비 작업 하나가 초당 메시지 10건 남짓, 운영은 작업 둘(concurrency 2)이라 20건쯤이다. 오픈 알림 신청자 1만 명(메시지 10개)은 수 초 안에 들어간다.
- **화면까지.** 저장된 알림은 그 회원의 연결을 가진 태스크가 다음 읽기(2초 간격)에서 찾아 보낸다 — 평균 1초, 길어야 2초 남짓이다. 읽기마다 앞 주기 시작 10초 전부터 읽으므로 1만 행이 한꺼번에 들어오면 그 뒤 10초 남짓 주기마다 1만 행(500행씩 20쪽)을 다시 읽고, 그다음부터는 창 안의 행만 읽는다.

`member.notifications.lag` 는 보낸 쪽 발생 시각부터 저장까지라 앞의 두 구간을 합친 값이다(화면까지는 들지 않는다). 당첨 인원이 많은 드로우 직후 잠깐 오르는 것은 정상이고, 몰린 일이 없는데 오르면 소비기가 멈췄거나 밀린 것이다.

**DB 장애 때.** 묶음(5건)을 차례로 처리하므로 DB 가 끊기면 건마다 연결 대기(Hikari 기본 30초)가 걸린다. 가시성(3분)을 묶음 최악 시간(150초)보다 길게 둬, 처리 중인 메시지가 다시 보여 받은 횟수가 헛되이 오르지 않게 한다.

**보안.** 큐에 보낼 수 있는 것은 IAM 으로 preorder · order 뿐이다. member 는 payload 의 recipientIds 를 믿고 저장하므로 보내기 권한을 늘릴 때 같이 본다. 문구 · target 은 프론트가 이스케이프해 그린다.

## 배포 순서

권한(member 받기 · DLQ 넣기, preorder · order 보내기)은 인프라 설정이 먼저 반영돼야 한다. 이벤트 종류가 하나라 member 가 먼저 나갈 필요는 처음 한 번뿐이다. 보내는 쪽이 먼저 나가면 메시지는 큐에서 기다리지만(보존 4일), 5분이 넘으면 메시지 나이 경보가 울린다 — 같은 배포로 함께 내보낸다.
