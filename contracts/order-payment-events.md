# order → payment 이벤트 계약

양쪽 구현의 기준이다. order 가 보내고(`order/outbox`, 표 `order_outbox_events`), payment 가 받는다(`payment/event` 의 `PaymentEventDispatcher`, 종류는 `InboundEventType`). 문서와 어긋나는 쪽이 고친다.
결과(승인 · 거절 · 환불)는 이 문서가 아니라 payment 가 `order-events` 로 보내는 이벤트(`ORDER_PAYMENT_SETTLED` · `ORDER_REFUND_SETTLED`)로 돌아온다.

## 전달

| 이벤트 | 큐 | 받는 쪽이 하는 일 |
| --- | --- | --- |
| `ORDER_REFUND_REQUESTED` | `payment-events` | 그 주문의 결제를 전액 환불한다(환불 거래를 연다) |
| `ORDER_PAYMENT_AUTHORIZING` | `payment-events` | 승인 요청이 payment 에 닿지 않은 결제창이면 복구에 넘겨 승인한다 |

- **최소 한 번.** 보내는 쪽은 업무 변경과 같은 트랜잭션에서 아웃박스에 적고, 커밋 직후 한 번 보내며 못 보냈으면 릴레이가 다시 보낸다. 같은 메시지가 두 번 갈 수 있다 — 받는 쪽은 두 번 받아도 결과가 같다(이벤트마다 아래).
- **순서 보장 없음.** 표준 큐다.
- **메시지 속성.** `eventType` · `eventId`(문자열). payment 가 지연을 두고 다시 보낸 사본에도 그대로 실린다.
- **처리 실패.** 모르는 종류 · 깨진 본문 · 다른 aggregate 는 예외로 올린다. 지우지 않아 다시 받다가 재수신 한도를 넘으면 `payment-events-dlq` 로 간다.
- **소비기.** payment 는 이 큐를 스레드 하나로 받는다. 처리에서 토스를 부르지 않는다 — 토스 호출은 복구 워커가 한다.

## 봉투

```json
{
  "eventId": "6f1c2a7e-0d3b-4c8f-9a51-2b7d8e4f0c19",
  "eventType": "ORDER_PAYMENT_AUTHORIZING",
  "aggregateType": "ORDER",
  "aggregateId": "0199a3f2-8a10-7b21-9c32-4d5e6f708192",
  "occurredAt": "2026-10-23T03:00:00.123456Z",
  "payload": { }
}
```

| 칸 | 뜻 |
| --- | --- |
| `aggregateType` | 두 이벤트 모두 `"ORDER"`. 다른 값이면 payment 가 거절한다(엉뚱한 대상의 결제를 건드리지 않게) |
| `aggregateId` | 주문 id(UUID 문자열) = payment 의 결제 대상 id. payload 에는 싣지 않는다 |

결제 키는 어느 이벤트에도 싣지 않는다.

## `ORDER_REFUND_REQUESTED` (order → payment)

```json
"payload": { "amount": 15000 }
```

| 칸 | 뜻 |
| --- | --- |
| `amount` | 주문 총액. payment 는 대조만 한다 — 다르면 ERROR 로 알리고, 환불은 결제 기록의 금액 · 결제 키로 한다 |

- **언제.** 결제된 주문을 취소 중으로 바꾼 트랜잭션에서 적는다(`SettlePreorderCancelService`).
- **중복.** 대상당 진행 중 환불은 하나라 다시 받아도 새로 열지 않는다. 이미 환불됐거나 마지막 환불이 확정 실패했어도 열지 않고 성공으로 끝낸다(확정 실패 뒤 다시 열지 않는다 — 결정 33).
- **결제 기록이 없으면** 다시 받아도 같으므로 예외로 올려 DLQ 로 보낸다(사람이 본다).

## `ORDER_PAYMENT_AUTHORIZING` (order → payment)

```json
"payload": { "providerOrderId": "3f2a9c1e-…", "amount": 15000 }
```

| 칸 | 뜻 |
| --- | --- |
| `providerOrderId` | 주문을 승인 중으로 바꾼 결제창(결제사 주문 번호, 토스 orderId) |
| `amount` | 알림을 적을 때의 주문 총액(승인 요청에 싣는 값과 같다). payment 는 결제창 금액과 대조만 한다 — 다르면 넘기지 않는다 |

order 의 결제 승인은 결제창 확인(시작 금지 + 확보) → [tx] 승인 중 전환 → payment 승인 호출 순서다(`order/pay/ConfirmPaymentService`). 승인 호출이 payment 에 닿지 않으면(payment 장애 · 재시작) 거래는 시작 전으로 남는다. 이 알림은 그 결제창을 백엔드 안에서 살리는 길이다 — 프런트의 재요청에 기대지 않는다.

- **언제.** 주문 결제의 승인 중 전환(결제 대기 → 승인 중)이 적용된 트랜잭션에서 적는다. 전환이 적용되지 않았거나(이미 승인 중 · 다른 상태) 트랜잭션이 되돌아가면 없다. 응모비 결제(`draw/DrawEntryPaymentService`)는 보내지 않는다.
- **결제 키.** 싣지 않는다. payment 는 결제창 확인 때 받은 키를 시작 전 거래에 적어 둔다 — 첫 확인에만 적는다(금액은 넘길 때 `amount` 로 대조한다). 다시 확인할 때 다른 키가 오면 지운다(어느 키가 승인 중 전환과 짝인지 모르면 넘기지 않는다). 승인 중 재요청이 시작 금지(확보 없음)로 물어도 지운다 — 결제할 수 없게 됐다는 판정이고, 결제 가능 확인이 일시 실패한 경우도 같다(안전 우선). 한 번 지운 키는 다시 적지 않는다.
- **알림이 나간 뒤 주문이 결제 대기로 돌아가면.** 넘겨지지 않는다. 되돌림은 끝난 거래(거절 · 만료) 또는 payment 의 "시작될 수 없다" 확언(번호 없음 · 금액 불일치)에서만 일어나고, 넘김도 같은 대상 · 금액을 대조한다.
- **승인 중인 주문이 결제할 수 없게 되면**(예약 취소 · 마감). 시작 금지 재요청이 넘김을 끄는 것은 그 호출이 payment 에 닿았을 때뿐이다. 닿지 못했거나 판정과 끄기 사이에 넘겨지면(또는 이미 넘겨졌으면) 결제할 수 없다고 판정된 주문도 청구될 수 있다. 승인이 늦게 끝나는 경우와 같은 부류로, 청구 뒤에는 order 의 기존 흐름(예약 취소 보류 → 결제 뒤 환불)이 처리한다.
- **받는 쪽이 하는 일**(`payment/confirm/ConfirmHandover`). 시각은 마지막 확보 시각(`reserved_at`, 결제창을 다시 확인하면 그때로 바뀐다 — 없으면 `created_at`)에서 잰다. 90초 · 10분 · 금액은 넘기는 UPDATE 의 조건에도 있어, 읽은 뒤 다시 확보된 결제창은 넘기지 않는다:

| 거래 | 하는 일 |
| --- | --- |
| 시작했거나 끝남(PENDING 이 아님) | 없음 — 평소는 이쪽이다 |
| PENDING · 결제 키 없음 · 금액이 `amount` 와 다름 | 없음 — 시작되지 않으면 만료(35분)가 거절을 보낸다 |
| PENDING · 확보 뒤 90초 전 | 남은 시간만큼 지연을 두고 같은 큐에 다시 보낸다. 그동안 직접 승인 요청이 먼저 시작한다(order 는 승인 응답을 최대 70초 기다린다) |
| PENDING · 확보 뒤 90초 ~ 10분 | 복구에 넘긴다 — 리스가 이미 끝난 PROCESSING 으로 바꾸고, 복구 워커가 적어 둔 키 · 거래의 멱등 키로 첫 승인을 보낸다. 결과는 `ORDER_PAYMENT_SETTLED` 로 온다 |
| PENDING · 확보 뒤 10분 이후 | 없음 — 토스 승인 창이 지났다. 만료가 거절을 보낸다 |

- **경합.** 넘김 · 직접 승인 요청의 시작 · 시작 금지 재요청의 키 지우기는 같은 "시작 전" 조건의 UPDATE 라 한쪽만 된다. 직접 요청이 졌으면 payment 는 PENDING 으로 답하고 결과는 이벤트로 간다.
- **중복.** 넘긴 뒤에는 시작 전이 아니라 다시 받아도 아무것도 하지 않는다.
- **결제창을 모르거나 다른 주문의 결제창이면** 계약이 어긋난 것이라 예외로 올려 DLQ 로 보낸다. order 는 payment 가 이 주문의 것으로 아는 결제창으로만 승인 중이 된다.
- **한계.** 결제창을 확인할 때마다 확보 시각이 새로 잡혀, 인증 뒤 10분이 지난 결제창도 넘겨질 수 있다(토스가 거절하므로 오결제는 아니다). 넘긴 거래는 토스 세션이 끝났어도 복구가 최대 약 15분 거절 · 재조회를 되풀이한 뒤 실패로 확정한다.
- **지표.** payment `payment.confirm.unreached{result}` — `HANDED_OVER`(넘김) · `TOO_LATE`(시작 전이었지만 10분이 지나 넘기지 못함).
