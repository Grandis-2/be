# NV-234 대기열 진입 급증 — 로컬 실측 결과

2026-10-04 측정. `entry-spike.js` 로 오픈 순간 예약 페이지 진입 급증(10초 동안 5,000명, 초당 500명)을 재고, 입장 속도별로 줄이 얼마나 빨리 빠지는지 · 순번이 지켜지는지를 봤다. 같은 조건을 두 번씩 쟀다.

## 요약

| 조건 | 바로 입장 | 줄 → 입장 | 거절 | 순번 역행 | 진입 p95 | 입장까지 중앙값 / p95 / 최대 |
|---|---|---|---|---|---|---|
| 입장 속도 100 (개선 전) | 70 | 4,930 (전원) | 0 | 0 | 30 · 79ms | 24 · 25초 / 39초 / 42초 |
| 입장 속도 500 (개선 전) | 350 | 4,650 (전원) | 0 | 0 | 31 · 42ms | 2초 / 31 · 32초 / 36초 |
| **입장 속도 500 (개선 후)** | 350 · 675 | 4,650 · 4,325 (전원) | 0 | 0 | 19 · 52ms | **1 · 2초 / 3초 / 4초** |
| **기본값 전역 150 · 모델 150** | 104 | 4,896 (전원) | 0 | 0 | 68ms (2회) | 13초 / 23 · 24초 / 26초 |

- 어느 회에서도 순번이 뒤로 간 사람이 없고(`position_regressions` 0), 줄에 선 사람은 전원 입장했다. 리더 지표(`waitingroom_admitted_total`)로 센 입장 인원도 k6 와 같다.
- 입장까지 걸린 시간은 줄 길이 ÷ 입장 속도와 맞는다(속도 100 이면 4,930명에 약 49초 → 마지막 진입자 기준 최대 약 40초).
- **개선 — 조회 간격**: 급증 직후에는 판정 재료가 아직 한산을 말해 모델 몫이 0이다. 예상 대기 시간이 "모름"이 되어 가장 긴 조회 간격(약 30초)을 받았고, 커서가 이미 지나간 사람이 30초 뒤에야 입장을 알았다(속도 500 의 p95 31초). 몫을 모르면 전역 속도와 모델 상한 중 작은 쪽으로 재게 고쳐 p95 가 3초가 됐다.
- **기본값 확정**: 전역 초당 입장 인원 150, 모델별 상한 150. 근거는 아래 "기본값".
- **운영 주의 — 예열**: 막 뜬 노드가 예열 없이 급증을 맞으면 진입 대부분이 503 이다. 오픈 전에 미리 늘린 노드는 오픈 전에 예열 요청을 흘려 둔다.

## 환경

| 항목 | 값 |
|---|---|
| 대기열 | `waitingroom` 부트 jar 2대(같은 호스트, 힙 최대 1GiB, Java 25), 서비스 포트 8085 · 8086, 관리 포트 9085 · 9086 |
| Redis | `redis:8` 컨테이너 하나(`maxmemory-policy noeviction`) |
| 회차 일정 | SQS 없이 `wr:products` 에 직접 넣음(`run-local.sh seed`) — 오픈 1분 전 ~ 2시간 |
| 인증 | member 와 같은 모양의 RS256 액세스 토큰(`make-tokens.py`), 대기열은 정적 공개키로 검증 |
| 부하기 | k6 v2.2.0, 같은 호스트. 진입은 노드 2대에 번갈아 보냄 |
| 호스트 | Intel i5-1335U(12 스레드) · 메모리 15GiB. 부하기 · 앱 · Redis 가 한 호스트를 나눠 쓴다 |
| preorder | 띄우지 않음 — 측정 범위는 진입 · 순서 조회 · 입장. 접수 쪽 한계는 preorder 실측(`preorder/load-test/NV-112-results.md`)을 근거로 쓴다 |

## 측정 방법

- 한 회는 새 모델(상품 ID)을 열고 입장 속도를 관리자 API 로 정한 뒤 `entry-spike.js` 를 돈다(`measure.sh`).
- `entry-spike.js` 는 회원 5,000명이 10초 동안 한 번씩 진입하고, 줄에 서면 응답의 `Retry-After` 대로 조회하다 입장권을 받으면 끝낸다. 같은 회원의 순서가 늘면 `position_regressions` 로 센다.
- 앱을 띄운 직후 첫 회는 JIT 예열 전이라 진입 응답이 크게 늦다. 측정 첫 회는 진입 p95 2.5초에 **80%(4,021건)가 Redis 시한(500ms)을 넘겨 503** 이었다(Redis 자체는 줄 서기 Lua 평균 0.16ms). 그래서 앱을 띄울 때마다 예열 한 회를 버리고 잰다.
- 입장 속도 500 은 모델 상한 기본값(150)에 막히지 않게 그 모델의 상한 운영값을 500 으로 올려 쟀다.

## 기본값

| 값 | 기본값 | 근거 |
|---|---|---|
| 전역 초당 입장 인원 | **150** | `preorder/load-test/NV-112-results.md`: preorder 1대(CPU 2 · 커넥션 풀 10)가 회차 하나에서 받는 접수 한계가 초당 약 200건. 입장한 사람은 120초 안에 접수하므로 입장 속도가 이를 넘으면 preorder 가 밀린다. 그 75% 로 여유를 둔다 |
| 모델별 상한 | **150** | 한 모델의 접수는 회차 행 잠금 하나를 지나므로 preorder 를 늘려도 모델 하나의 한계는 그대로다. 전역 속도를 올려도 모델 하나가 이를 넘지 않게 |

preorder 를 늘리면 전역 속도만 관리자 API(`PUT /api/v1/admin/waitingroom/admission-rate`)로 올린다. 대기열 쪽 한계는 이 측정 범위(초당 500명 진입 · 500명 입장)에서 드러나지 않았다 — 노드 2대에서 진입 p95 가 수십 ms 다.

## 재현

```bash
./gradlew :waitingroom:bootJar
cd waitingroom/load-test
python3 make-tokens.py --count 5000 --out build      # 회원 토큰 · 관리자 토큰 · 공개키
./run-local.sh start 2                                # Redis + 대기열 2대
./measure.sh 200 150 warmup || true                   # 예열(실패해도 버린다)
./measure.sh 201 150 default-run1                     # 기본값
./measure.sh 203 500 rate500-run1 500                 # 속도 500 · 모델 상한 500
./run-local.sh stop
```

결과는 `build/<이름>.txt`(k6 요약 + 리더가 들인 인원) · `build/<이름>.json` 에 남는다.

## 측정하지 않은 것

- 접수 전달(preorder 연결)과 관측 브레이크의 실제 작동 — preorder 를 함께 띄운 측정은 배포 환경에서.
- 노드 수 · Redis 분리 · 네트워크 지연 — 모두 한 호스트라 노드 사이 지연이 없다.
