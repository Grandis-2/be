# NV-112 사전예약 접수 급증 — 로컬 실측 결과

2026-10-01 측정. `accept-spike.js` 를 로컬 컨테이너 환경에서 세 규모로 쟀다(회당 500 · 1,000 · 5,000건). 500 · 5,000건은 규모마다 6번 실행해 첫 실행을 워밍업(JIT 컴파일 · 캐시 · 커넥션 풀 · SQS 클라이언트 초기화)으로 버리고 그다음 5번(1~5회)을 측정했다. 1,000건은 이 방식에서 1회가 덜 데워진 채 측정돼, JIT 가 잠잠해질 때까지 워밍업하고 회마다 정상 상태를 확인한 뒤 시작하는 방식으로 다시 쟀다(아래 "측정 방법").

## 요약

| 규모 | 부하 | preorder 자원 | 성공률 | p95 | p99 | 판정 |
|---|---|---|---|---|---|---|
| 500건 | 초당 50 × 10초 | 메모리 2GB · **CPU 제한 없음** | 100% | 15.3ms | 23.6ms | 여유 — 경합 없음 |
| 1,000건 | 초당 100 × 10초 | 메모리 2GB · **CPU 2** | 100% | 130.0ms (꼬리 1회 제외 15.3ms) | 209.6ms (꼬리 1회 제외 32.1ms) | 버팀 — 정상 상태는 여유, 간헐적 꼬리 지연 |
| 5,000건 | 초당 500 × 10초 | 메모리 2GB · **CPU 2** | 27.5% | 2,673.9ms | 2,793.8ms | 한계 초과 — 커넥션 풀 고갈 |

- 인스턴스 1대(CPU 2 · 커넥션 풀 10)가 받는 접수 한계는 **초당 약 200건** 근처다. 5,000건 측정에서 가장 많이 받은 회가 10초에 2,235건이었다.
- 어느 규모 · 어느 회에서도 접수된 건은 유실 · 중복 없이 정확했다(정합성 검사 전부 0, 발행 유실 0). 실패한 요청은 커넥션을 얻지 못해 트랜잭션 전에 끝나 흔적이 남지 않는다.

## 측정 방법

**지표 계산** — 아래 세 열은 모두 Micrometer 타이머(누적 횟수 `_count` · 누적 시간 `_sum`)다. 회마다 k6 시작 직전과 k6 종료 3초 뒤 `/actuator/prometheus` 를 받아 차이를 냈다.

| 열 | 출처 | 계산 | 주의 |
|---|---|---|---|
| 회차 잠금 대기 평균 | `preorder.campaign.lock.wait` — `PreorderAcceptTransaction` 이 `campaigns.lockForAccept`(회차 행 `SELECT … FOR UPDATE`)를 감싼다 | Δ누적시간 ÷ Δ횟수 | 잠금 대기 + 쿼리 시간. 커넥션은 이미 잡은 뒤라 커넥션 대기는 들어가지 않는다 |
| 커넥션 획득 대기 평균 | Hikari 기본 지표 `hikaricp.connections.acquire` | Δ누적시간 ÷ Δ횟수 | **요청 1건이 아니라 커넥션 획득 1번 기준.** 구간 안의 모든 획득(접수 트랜잭션 · 커밋 직후 발행의 완료 기록 · 릴레이 · 지표 갱신)이 들어간다. 안정되면 요청 1건에 약 3번 |
| GC 멈춤(횟수 / 합계) | JVM 기본 지표 `jvm.gc.pause` | 모든 종류의 Δ횟수 · Δ누적시간 | 멈춤(STW) 단계만(G1 young · mixed · remark · cleanup). 동시 마킹은 빠진다 |

응답 시간은 k6 가 잰 접수 요청(`http_req_duration{name:accept}`), CPU 는 `docker stats`(컨테이너, 200% = 2코어)와 `/proc/stat`(호스트), 메모리는 `docker stats` 0.5초 간격 최대값이다.

**1,000건 재측정 이유** — 처음 1,000건 측정(워밍업 1회 + 고정 75초 휴지)의 1회가 p95 875ms · p99 1,409ms 로 다른 회(p99 25~45ms)와 크게 달랐다. 회차별 `jvm.compilation.time` 과 시작 시 미발행을 보니 원인이 둘이었다.

| 처음 측정 | 실행 10초 동안 JIT 컴파일 | 시작 시 미발행 |
|---|---|---|
| 워밍업 | 16.9s | 0 |
| 1회 | 10.2s | 206 |
| 2회 | 6.0s | 93 |
| 3~5회 | 3.4 · 1.5 · 2.7s | 0 |

- JIT 미완료: CPU 2 중 절반 가까이를 컴파일러가 썼다. 워밍업에서 절반이 실패해 성공 경로가 충분히 돌지 않았고, CPU 제한이 없던 500건 측정에서는 남는 코어로 가려졌다.
- 밀린 발행: 워밍업의 미발행이 75초 휴지 안에 다 빠지지 않아(릴레이는 1분 뒤부터 10초에 100건) 다음 회가 그것을 안고 시작했다.

그래서 1,000건은 시간이 아니라 상태로 시작을 정했다 — 워밍업은 실행 중 JIT 가 10초당 1초 아래가 될 때까지(최대 8번, 첫 번은 초당 50 × 20초, 이후 초당 100 × 10초), 회마다 미발행 0 이고 쉬는 10초 동안 JIT 0.5초 미만일 때 시작. 실제로 워밍업 JIT 는 10초당 9.6 → 5.7 → 4.9 → 3.2 → 1.2 → 2.9 → 1.5 → 1.3초로, 부하 중에는 1초 남짓에서 바닥을 쳐 8번을 다 돌았다. 5,000건도 같은 방식의 문제가 있으나 과부하가 원인이라 결론(한계 초과)은 달라지지 않는다.

## 정합성 (`invariant-check.sql`)

500건 6회 · 1,000건(처음 측정 6회 · 재측정 5회 · 진단 10회) · 5,000건 6회 모두 순번 중복 · 순번 빈틈 · 발급 순번 불일치 · 입장권 중복 · 등록 작업 불일치 · 등록 이벤트 불일치가 **0**, 발행이 다 빠진 뒤 미발행 **0** 이다. `not_final` 은 worker 를 띄우지 않아 외부 등록이 일어나지 않은 결과이며 측정 대상이 아니다.

## 발견 사항 · 개선 거리

1. **커넥션 풀 고갈이 HTTP 500 으로 나간다** — 일시적 과부하인데 클라이언트가 다시 시도해도 되는지 알 수 없다. 503 + `Retry-After` 로 바꾸는 것이 맞다.
2. **커넥션 풀 10이 1차 병목** — CPU 2 인스턴스 1대의 처리 한계는 초당 약 200건. 목표 초당 500건이면 인스턴스 수 · 풀 크기(그리고 RDS 최대 연결 수)를 함께 정해야 한다.
3. **차가운 인스턴스는 부하를 못 받는다** — CPU 2 에서 차가운 JVM 이 초당 100건을 받으면 절반이 실패했고, 데워지는 데 1,000건 실행 7~8번이 걸렸다. 오픈 전에 새 인스턴스를 데우는 절차(사전 호출)와 그 완료 판정(JIT 안정)이 필요하다.
4. **발행 처리량** — 커밋 직후 발행 동시 32 가 넘치면 릴레이(10초에 100건)로 넘어가 외부 등록 시작이 수 분 늦어진다. `nova.outbox.concurrency` · `relay-batch` · `relay-interval` 을 목표 처리량에 맞춰야 한다.
5. **CPU** — 5,000건에서 CPU 2 가 포화됐다. 태스크 CPU 크기도 인스턴스 수와 함께 정할 대상이다.
6. **간헐적 꼬리 지연** — 정상 상태에서도 7회에 1번꼴로 회차 행 잠금 보유가 길어져 p99 가 수백 ms 로 튀었다. 회차 행 하나에 접수가 줄을 서는 구조라 잠금을 쥔 트랜잭션이 잠깐만 멈춰도 뒤가 모두 밀린다. 원인(CPU 스로틀링 등)은 확정하지 못했다 — 운영 환경에서는 cgroup 스로틀링 지표를 함께 봐야 한다.

## 한계

- 로컬 단일 호스트: 부하기 · DB · 앱이 같은 CPU 를 나눠 쓰고, 네트워크 지연이 없다. MySQL 커밋은 로컬 디스크다(RDS 와 다르다).
- 인스턴스 1대 기준이다(운영은 ECS 6~12대). 여러 대에서는 회차 행 잠금 경합이 인스턴스를 넘어 생긴다 — 그 영향은 이 측정에 없다.
- catalog 는 대역이고 캐시되어 접수 경로의 외부 호출 비용이 빠져 있다. worker · order 는 띄우지 않았다.
- 1,000건의 5회 평균에는 꼬리 지연 1회가 들어 있다(제외 평균을 따로 적었다). 그 원인은 확정하지 못했다.
- 로컬 MySQL 은 기본값(버퍼 풀 128MB · redo 로그 100MB · binlog 와 커밋마다 fsync 두 번)이다. 1,000건에서는 압박이 없었지만 RDS 설정과 다르다.

## 다시 재는 방법

레포에 시드 · 키 · 스크립트를 두지 않았다. 같은 조건으로 다시 재려면:

1. 컨테이너: MySQL 8.4 · Redis · Floci(`docker/floci/create-queues.sh` 로 큐 생성) · WireMock(catalog 응답), `flyway-project/flyway.sh migrate`.
2. 임시 시드: 회원(규모만큼), 회마다 상품 · 옵션(ACTIVE, PREORDER) · 열린 회차 · 배송 차수.
3. RSA 키 쌍을 만들고 공개키를 `jwt.public-keys.<kid>` 에, 개인키로 위 형식의 토큰을 `customerId,accessToken` CSV 로.
4. preorder 컨테이너를 `--memory=2g --memory-swap=2g --cpus=2` 로, `WAITING_TOKEN_SECRET` 을 주고 기동.
5. 워밍업은 실행 중 JIT 컴파일 시간(`jvm_compilation_time_ms_total` 차이)이 10초당 1초 안팎으로 내려올 때까지 반복하고, 회마다 미발행 0 · 쉬는 10초 JIT 0.5초 미만을 확인한 뒤 시작한다.
6. 회마다 `k6 run --summary-trend-stats "avg,min,med,max,p(90),p(95),p(99)" -e RATE=… -e DURATION_SECONDS=10 -e PRODUCT_ID=… -e OPTION_ID=… -e TICKET_SECRET=… -e TOKENS_FILE=tokens.csv accept-spike.js`, 끝나면 `invariant-check.sql`. 실행 전후 `/actuator/prometheus` 를 받아 차이를 본다.
